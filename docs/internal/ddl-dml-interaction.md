# DDLとDMLの同時実行の制御について

2025-06-26 kurosawa

## 本文書について

tsurugiに対してDDLとDMLを混在して実行した場合の仕様が明確でなく、排他制御の実装も不十分だった。この問題を解決するための設計について記述する。

## 用語

- DML
  - SELECT
  - INSERT
  - UPDATE
  - DELETE

- DDL 
  - CREATE/DROP TABLE
  - CREATE/DROP INDEX

- ステートメント
  - DMLまたはDDLの一文

- クエリ
  - SELECT文のみからなるステートメント
  - リザルトセットをもつ
  - INSERT ... SELECTは含まない

- リクエスト
  - SQL実行エンジンに送信する処理要求の単位
  - ステートメントの実行はリクエストとして要求される
  - ステートメント以外のリクエストもある
    - begin/commit, prepare, describe tableなど

## 外部仕様

### テーブル閉塞

原則としてテーブルに対するアクセスを閉塞することにより、DDLとDMLの実行可能区間を分離する

- 操作対象のテーブルに関連づいた(共有)ロックを取得し、取得できた場合のみ実行するというモデル
  - DDLは対象テーブルに対する排他ロックを取得し、トランザクションの完了まで保持する
  - DMLは対象テーブルに対する共有ロックを取得し、ステートメントの完了まで保持する
  - 共通のテーブルを操作対象として持たないステートメント同士は排他されず、それぞれ独立して実行可能
- DMLの実行区間ではDDLを開始できない
  - DMLはステートメントの開始時にテーブルに対する共有ロックを取得する
  - 共有ロックは複数のDMLが同時に取得可能なのでDML同士は並列に実行可能
  - DDLは排他ロックが必要なのでDMLステートメントが完了するまでは取得できない
- DDLを実行したトランザクションが完了するまではDMLは開始できない
  - DDLはそのトランザクションにおいて最初に実行された際に操作対象のテーブルに対する排他ロックを取得する
  - トランザクションがコミット(shiarkami precommit)かアボートするまでこのロックは保持される
  - 同一トランザクションでDDLが2回以上実行された場合、初回に取得したものと同じ排他ロックを使用する
    - 操作対象のテーブルが実行ごとに異なる場合、排他ロックは同じものを使い、そのロック対象を拡張する
  - 同一トランザクションでDDL実行後にDMLが実行された場合、DMLは排他ロックを親とする共有ロックを取得する
    - この共有ロックを保持するDMLは親が排他ロックしているテーブルに対してもアクセス可能
    - 共有ロック自体はDMLステートメントの完了時に開放。排他ロックはトランザクション完了まで保持される。
- DDL同士の場合、先にDDLを実行したTXが排他ロックを持ち、そのトランザクションの終了後まで別トランザクションのDDLは開始できない
  - 同一トランザクションを使った複数のDDLが並行するケースは考慮外
    - 将来的にはDDLをstickyタスクにすることで対応予定
- DDL/DMLいずれの場合も、ロックが取得できない場合はエラーが戻される。なんらかの処理を待機することはしない
  - 将来的には待機を検討するかもしれない

### prepared statement

- prepared statement がロックする対象は prepare 時に決まり、実行のたびには決め直さない
- DDL によって対象テーブルが削除・再作成された後(DROP TABLE, TRUNCATE TABLE)は、それより前に prepare した文の実行はエラー( `DML operation was blocked by DDL operation` )になる
  - 同一トランザクション内で DDL の後に実行した場合も同様である
  - 再度 prepare すれば実行できる(tsurugi-issues #702 の対応が入るまでの扱い)

## 1.5での制限事項

- DDLはCREATE TABLE/DROP TABLEのみをサポート
  - CREATE INDEX/DROP INDEXも本文書の排他処理の対象だが1.5では未実装

## post-1.5 で対応予定のトピック

カッコ内はtsurugi-issuesのissue番号

- DDL/DML混在問題の残り (#177, #1137)
  - トランザクションによって使用されたテーブルをコミット前に別トランザクションからDROPするとshirakamiがクラッシュ
- DDL処理を行ったトランザクションをアボートするとシステムテーブルにゴミが残ったり不整合な状況になる (#448)
  - トランザクションアボート時に補償トランザクションを実行し不整合を修正する
  - DDLをロールバック可能にするわけではないが、補償トランザクションの内容によってはロールバックされたかのように見えるケースもある
- Prepared statementを保持したままテーブルを再作成してアクセスすると不安定な状態になる(#702)
  - DDL実行時にprepared statementを使用不可としてマークし、使用した際にはエラーにする
- truncate文 (#812) alter table rename文 (#1089)
  - 内部的な名前/IDのマッピング変更により対応

## 細かい注意点

- CREATE TABLEはその処理中にロック対象を作成する、またDROP TABLEは処理中にロック対象を削除することになる
  - ロックが有効なのはこれらの作成から削除までの間
  - トランザクションが未完了な時点でも、削除されたテーブルに対するロックは自動的に開放される
- ステートメントの実行区間(開始から完了)はSQL実行エンジンが定義するもので、クライアントから観察されるものと少し異なることがある
  - INSERT/UPDATE等のリザルトセットを持たないDMLステートメントはその処理が完了するまで
    - クライアントが観察する実行区間とほぼ一致
  - クエリはSQL実行エンジンんが結果セットをエンドポイントに渡し終え、完了通知を送った時点で完了
    - クライアントがそれを読み出したかどうかは関係ない

## 内部設計

外部仕様の「テーブルに対するロック」は、内部ではストレージエントリに対するロックで実現する。テーブルとエントリの対応は DDL によって変わる(TRUNCATE TABLE は対応先を新しいエントリに付け替える)ため、本節ではロックの対象をエントリとして記述する。

### ロックの対象

- ロックの単位は、プライマリインデックスのストレージエントリ( `storage_manager` の `storage_control` )である。以下では、単に「エントリ」と書く
  - セカンダリインデックスのエントリはロックしない。セカンダリインデックスは、それが属するプライマリのエントリのロックによって保護される
- テーブルのロックとは、そのテーブル名が現在対応しているエントリのロックである
  - テーブル名の対応先は DDL によって変わりうるので、同じテーブルのロックでも、時点によって対象のエントリが異なる
- DDL の排他ロックは、トランザクション( `transaction_context` )が `storage::unique_lock` として保持し、トランザクションの完了時に解放する
  - 1つのトランザクションが複数のエントリを排他ロックすることがある。TRUNCATE TABLE は旧エントリと新エントリの両方をロックし、複数の DDL を実行したトランザクションはそれぞれの対象をロックする
- DML の共有ロックは、リクエスト( `request_context` )が `storage::shared_lock` として保持し、リクエストの完了時に解放する
  - 対象は、DML が参照するテーブルの名前から、SQL の解析時(prepared statement では prepare 時)に引いたエントリの集合である
  - 同一トランザクションの排他ロックを親とし、親が保持するエントリについては共有ロックの取得を省略する

### エントリのロックが保護するもの

エントリ E のロックは、次のものを保護する。

1. E の状態(削除予約されているかどうか、ストレージキー、権限情報)
2. E の実体のストレージ、E に属するセカンダリインデックスのエントリ、およびその実体のストレージ
3. E を指す名前の対応(E を指すテーブル名、E に属するセカンダリインデックスのエントリを指すインデックス名)
4. 3 の名前で参照されるテーブル・インデックスの定義(`configurable_provider` に登録されたもの)
5. E のテーブルが所有するシーケンスのメタデータ(詳細は「テーブルが所有するシーケンス」を参照)

E を指していない名前の対応は、E のロックでは保護されない。例えば、まだ登録されていない名前や、別のエントリに付け替えられた後の名前である。

#### 共有ロック(DML)が保証すること

- E が有効(削除予約されておらず、その名前の対応先である)な状態で E の共有ロックを保持している間、上記 1〜5 は変化しない
  - したがって DML は、共有ロックを保持している間であれば、名前からストレージを引き直しても E(およびそのセカンダリ)に到達する
- DML は、共有ロックの対象 E を、ロックを取得する前に名前から引いて決めている。その後に名前が別のエントリに付け替えられていても、E のロックはそれを検出できない。そのため、ロックを取得した後に、E が今もその名前の対応先であること(E が削除予約されておらず、E の名前が E を指していること)を確認する
  - 名前の対応先の変更(名前を E から外す、別のエントリに付け替える)は、E の排他ロックを保持している間にだけ行われるので、共有ロックを取得した後のこの確認で十分である

#### 排他ロック(DDL)が許すこと

- エントリ E の排他ロックを保持している間、DDL は E について上記 1〜5 を変更してよい
- 名前の対応先を変更する場合は、変更前と変更後の両方のエントリの排他ロックを保持していなければならない
  - TRUNCATE TABLE:旧エントリ(削除予約する)と新エントリ(名前を付ける。名前は旧エントリから新エントリへ直接付け替え、どのエントリも指さない瞬間を作らない)
  - DROP TABLE:旧エントリ(名前を外して削除予約する)
  - CREATE TABLE:新エントリ(名前を付ける)
- 新しく名前で引けるようにするエントリは、名前で引けるようになる前に排他ロックしていなければならない

#### テーブルが所有するシーケンス

テーブルが所有するシーケンスは、自動生成された主キー列と generated identity 列のために CREATE TABLE が作成するものである(名前は `generated_sequence_name_prefix` で始まる)。ユーザーが独立して作成するシーケンス(CREATE SEQUENCE)は現在ない。このシーケンスはテーブルのプライマリのエントリ E のロックで保護する。

シーケンスは次の要素からなる。

- シーケンス定義: `configurable_provider` に登録された `yugawara::storage::sequence`(名前、定義ID、初期値、増分、最小値・最大値、循環の有無)。列のデフォルト値として、テーブル定義から参照される
- システムテーブル `__system_sequences` の行: 定義IDとシーケンスIDの対応。DDL を実行するトランザクションを使って書き換える
- `executor::sequence::manager` のエントリ: 定義IDをキーとするインメモリのエントリで、シーケンスID、定義の内容のコピー( `sequence::info` )、現在値を持つシーケンスオブジェクト( `sequence::sequence` )からなる
- cc エンジン(sharksfin/shirakami)上のシーケンス: シーケンスIDで識別され、現在値とバージョンを永続化する。作成・削除はトランザクションの外で即座に行われる

上記のうち、現在値以外がメタデータであり、E のロックで次のように保護する。

- DML(E の共有ロックを保持)はシーケンスの値を進めるだけで、メタデータは変更しない
  - 定義IDから `manager::find_sequence()` でシーケンスオブジェクトを引き、`sequence::next()` で値を進め、`manager::notify_updates()` でその値を自トランザクションの更新として cc エンジンに渡す( `fill_record_fields.cpp` の `next_sequence_value()` )。これらは同じ文の中で行い、シーケンスオブジェクトへのポインタを文の終了後まで保持しない
  - 値を進める操作はシーケンスオブジェクト内のアトミック変数の CAS で行うので、DML 同士は共有ロックのまま並行して値を進められる
  - 共有ロックを保持している間は、次の DDL によるメタデータの変更やシーケンスオブジェクトの破棄は起こらない
- DDL(E の排他ロックを保持)は次のように変更する
  - CREATE TABLE: シーケンス定義に定義IDを割り当て、manager のエントリと cc エンジン上のシーケンスを作成し、`__system_sequences` に行を追加する。これはテーブルのエントリを作成する前に行うが、シーケンス定義はテーブル定義から参照されて初めて DML から使われ、テーブル定義が名前で引けるようになるのは新エントリを排他ロックした後である
  - DROP TABLE: cc エンジン上のシーケンスを削除し、manager のエントリ(シーケンスオブジェクトを含む)を破棄し、`__system_sequences` の行とシーケンス定義を削除する
  - TRUNCATE TABLE ... RESTART IDENTITY: シーケンスの値だけを初期状態に戻し(`sequence::reset()` )、その値を DDL のトランザクションの更新として cc エンジンに渡す。シーケンス定義、定義ID、シーケンスID、`__system_sequences` の行、シーケンスオブジェクトは変更しない。RESTART IDENTITY を指定しない場合はシーケンスに触れない
- 実行計画は解析時に読んだ定義IDを含む。DROP TABLE や TRUNCATE TABLE より前に解析(prepare)した文は、ロックの取得後のエントリの確認でエラーになるので、削除済みの定義IDでシーケンスを引くことはない。TRUNCATE TABLE は定義IDを変えないので、その後に解析した文も同じシーケンスを使う

### ロックで保護しないもの

- トランザクション単位のストレージの使用
  - 共有ロックはリクエスト単位で解放されるが、トランザクションはその後もストレージを参照し続けうる。これは参照カウントによる遅延削除で保護する([lazy-delete-storage.md](lazy-delete-storage.md))
- SQL の解析時に読むテーブル定義
  - 解析(prepare を含む)はロックを取得せずにテーブル定義と名前の対応を読む。DDL が定義を差し替えている途中を読んだ場合は解析自体がエラー(compile_exception)になることがある(既知の制限)
  - 定義の差し替えは複数の手順(テーブル、プライマリインデックス、セカンダリインデックスの登録)に分かれ、その途中の状態から作られた実行計画は、ロックの取得後の確認(エントリが名前の対応先であること)では検出できない。途中の状態から作られた実行計画が実行されると、例えばセカンダリインデックスへの書き込みが欠けうる
  - TRUNCATE TABLE は定義を変更しない(`configurable_provider` の定義のオブジェクトをそのまま維持する)ので、この問題は起きない。以前は定義を登録し直しており、並行する DML の解析エラーやセカンダリインデックスの不整合が起きていた(tsurugi-issues #1587)
  - 定義を変更する DDL(CREATE INDEX、DROP INDEX、将来の ALTER TABLE など)では起きうる。解決するには、解析時に読んだ定義がロックの取得後も変わっていないことを確認する仕組み(定義のバージョンなど)が必要である
